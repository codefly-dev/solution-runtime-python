# solution-runtime (python)

Generic Python runtime for **codefly solutions**. Twin of solution-runtime-go:
registration (host + gateway, heartbeat), CORS, Module Federation asset serving,
the capability handshake, the manifest, and a bearer-forwarding gateway client.

```python
from solution_runtime import Gateway, Solution

def handler(gw: Gateway) -> dict:
    resp = gw.unary("/pkg.Service/Method", Request(), Response)
    return {...}

Solution(id="my-solution", title="My Solution").handle("/thing", handler).serve()
```

The gateway URL, the caller's bearer, and the wire protocol are hidden.

## Per-solution SDK (`solution-sdk`)

Threading a raw procedure string — `gw.unary("/saas.accounts.v1.AuditService/QueryAuditLog", req, Resp)` — and vendoring a whole module's generated `gen/` tree are the two things every solution used to repeat. `solution-sdk` replaces both: a solution declares the module dependencies it calls, and the generator builds **one SDK for that solution, carrying only the functionality it declares**, vendored so handlers use it out of the box:

```python
from _sdk.accounts import accounts

def last_login(gw: Gateway) -> dict:
    resp = accounts(gw).audit().query_audit_log(QueryAuditLogRequest(page_size=20))
    ...
```

Install the tool where SDKs are regenerated (it is a build-time dependency, not needed at serve time):

```bash
pip install 'solution-runtime[sdk]'
```

### Declare dependencies

The solution owns a `solution-sdk.yaml`:

```yaml
version: 1
out: backend/_sdk # where the vendored SDK lands
dependencies:
  - module: accounts # the entry-point name: accounts(gw)
    package: saas.accounts.v1 # the proto package to bind
    source:
      repo: https://github.com/codefly-dev/module-saas-starter
      ref: a44ac5aa0b9d019ad8ad659b474c36d81bf9ed50 # pinned, like saas-sdk-go's SOURCE.txt
      subdir: module/services/accounts/proto
    services: [AuditService] # optional: the subset actually used
```

### Generate

```bash
solution-sdk sync # reads solution-sdk.yaml, writes out/
```

`sync` fetches each proto at its pinned ref and produces two layers into `out/`:

1. **Message bindings** (`*_pb2`, `*_pyi`), generated by `codefly generate proto` — all proto codegen goes through codefly, never a bespoke `buf` invocation.
2. **A gateway-bound facade** (`<module>.py`), emitted from the proto descriptor: one class per service, one method per RPC, each routing through this runtime's `Gateway.unary` seam. The procedure string and response type are baked in by the generator, so a handler never threads either — and only the declared `services` are present.

The vendored tree carries a `SOURCE.txt` recording every pin (the same drift guard `saas-sdk-go` keeps). The runtime itself stays module-agnostic: the facade binds to `Gateway.unary`; the runtime never learns what "accounts" is, so a second module's SDK binds the same way.

`sync` requires `codefly` (which needs Docker for its proto companion) and network access to fetch the pinned proto; the facade generator alone is offline. The facade generator is also a standalone protoc/buf plugin (`protoc-gen-solution_facade`) for pipelines that prefer to wire it into their own `buf.gen.yaml`.
